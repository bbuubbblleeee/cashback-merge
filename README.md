# Проект 2. Cashback Merge

## Суть

Мини-игра в духе 2048 на поле `4x4`. На поле появляются плитки с кэшбэком,
две одинаковые объединяются в следующую:

```text
1% + 1% = 2%    2% + 2% = 4%    ...    16% + 16% = 32%
```

У игрока ограниченное число ходов, цель — собрать максимальный кэшбэк.

Но у проекта есть второй, продуктовый слой. По итоговой плитке начисляется
награда, и эта награда стоит компании денег. Поэтому максимальную награду
должна получать ограниченная доля игроков — например, не больше `20%`.
Проверяется это симуляцией на тысячах «игроков» до запуска акции.

---

## Что реализовано
1. Считывание конфигурации кампании из файла .json и ее преобразование в объект `CampaignConfig`
2. Валидация конфигурации
3. Поле с плитками уровня кэшбека, одна плитка на клетку
4. Генерация плиток с кэшбеком
5. Создание начального состояния поля по seed
6. Состояние сессии (количество сделанных ходов и завершена ли игра)
7. Текстовый вывод поля
8. Инварианты:
   1. Поле квадратное (размер поля считывается из конфигурационного файла)
   2. movesLimit > 0
   3. Spawn-правила не пусты, вероятности корректны и в сумме дают ровно 1
9. Юнит-тесты


## Как запускать

```bash
./gradlew check                        # тесты + линтеры
./gradlew run                          # запуск со случайным словом
```

Нужен **JDK 25 или новее**.

## Какие решения были приняты
1. Проценты и вероятности сохраняются в виде BigDecimal для точного хранения
2. Spawn-правила хранятся в списке для сохранения порядка вхождения (это важно при генерации плитки, процесс генерации плитки описан ниже)
3. Устанавливается 3 в качестве максимального количества цифр после запятой у BigDecimal. Было сделано так для удобства при генерации плитки. Я считаю, что такого количества достаточно по бизнес логике
4. При генерации плитки выбор значения кэшбека происходит следующим образом
   1. Генерируется число от 0 до 1
   2. Проходимся по spawn-правилам и накапливаем текущую вероятность
   3. Как только сгенерированное число становится меньше текущей накопленной вероятности - берем текущее значение кэшбека из цикла
   То есть мы разбили участок (от 0 до 1) на отрезки, соответствующие spawn-правилам, взяли число от 0 до 1 и посмотрели какому отрезку это число соответствует
5. При генерации плитки мы выбираем из еще не занятых клеток поля. Если все плитки были заняты - выкидывается исключение
6. Сообщения об ошибках были вынесены в `messages.properties`
7. Координаты одной клетки поля были вынесены в класс `Position`, чтобы было удобнее работать с ними вне класса Board. Становится понятно, где строка, а где столбец (при int[] непонятно в каком порядке передавать
8. Поля, находящиеся в конфиге, но отсутствующие в `CampaignConfig` игнорируются
9. Если есть поля, находящиеся в `CampaignConfig`, но отсутствующие в конфиге, выбрасывается исключение
10. При добавлении/удалении плитки с поля, возвращается новое поле. Это сделано ради инкапсуляции, чтобы другие обьекты не могли поменять состояние поля
