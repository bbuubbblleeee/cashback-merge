# Проект 2. Cashback Merge

## Суть

Мини-игра в духе 2048 на поле `4x4`. На поле появляются плитки с кэшбэком,
две одинаковые объединяются в следующую:

```text
1% + 1% = 2%    2% + 2% = 4%    ...    16% + 16% = 32%
```

У игрока ограниченное число ходов, цель — собрать максимальный кэшбэк.

Но у проекта есть второй, продуктовый слой. По итоговой плитке начисляется
награда, и эта награда стоит компании денег. Поэтому максимальную награду
должна получать ограниченная доля игроков — например, не больше `20%`.
Проверяется это симуляцией на тысячах «игроков» до запуска акции.

---

## Что реализовано

### MR1 - модель, конфиг, начальное состояние
1. Чтение конфигурации кампании из JSON-файла и её преобразование в объект `CampaignConfig`
2. Валидация конфигурации
3. Поле с плитками кэшбэка, одна плитка на клетку
4. Генерация плиток с кэшбэком по spawn-правилам
5. Создание начального состояния по seed: на пустое поле ставятся две стартовые плитки
6. Состояние игровой сессии: поле, количество оставшихся ходов, score и статус игры (`IN_PROGRESS` / `FINISHED`)
7. Текстовый вывод поля
8. Инварианты:
   1. Поле квадратное (размер поля задаётся в конфиге), координаты всегда в границах поля
   2. `movesLimit > 0`
   3. Spawn-правила не пусты, вероятности корректны и в сумме дают ровно 1

### MR2 - движок ходов
1. Ходы `UP / DOWN / LEFT / RIGHT`
2. Сдвиг и объединение плиток по правилам 2048:
   ```text
   [1, 1, ., .] -> LEFT -> [2, ., ., .]
   [1, 1, 1, .] -> LEFT -> [2, 1, ., .]
   [1, 1, 1, 1] -> LEFT -> [2, 2, ., .]
   [2, 2, 4, 4] -> LEFT -> [4, 8, ., .]
   ```
3. Одна плитка не объединяется дважды за ход: `[1, 1, 2, .] -> LEFT -> [2, 2, ., .]`, а не `[4, ., ., .]`
4. Невалидный ход (ничего не сдвинулось и ничего не слилось) не меняет поле, не тратит ход и не создаёт новую плитку
5. После валидного хода появляется ровно одна новая плитка
6. Подсчёт score (правило описано ниже)
7. Завершение игры (условия описаны ниже). Достижение плитки `32%` игру не заканчивает
8. Проверка, остались ли на поле доступные ходы


## Правила игры

### Score
За каждое слияние к score прибавляется значение получившейся плитки:

| Слияние | Очки |
|---|---|
| 1% + 1% = 2% | +2 |
| 2% + 2% = 4% | +4 |
| 16% + 16% = 32% | +32 |

Например, `[2, 2, 4, 4] -> LEFT -> [4, 8, ., .]` даёт `+4 + 8 = +12`.
Score увеличивается только при слияниях: обычный сдвиг без слияний и появление новой плитки очков не дают.

### Завершение игры
Игра переходит в статус `FINISHED`, когда выполнено одно из условий:
1. Закончился лимит ходов (`movesLimit`). Считаются только валидные ходы
2. На поле не осталось ни одного валидного хода (поле заполнено, и слить нечего)


## Как запускать

```bash
./gradlew check                        # тесты + линтеры
./gradlew run                          # загружает конфиг и печатает начальное поле
```

Нужен **JDK 25 или новее**.

## Какие решения были приняты

### Конфиг и генерация плиток
1. Проценты и вероятности хранятся в `BigDecimal`, чтобы не терять точность
2. Spawn-правила хранятся в списке, чтобы сохранить их порядок: от порядка зависит генерация плитки
3. У вероятностей допускается не больше 3 знаков после запятой. Так удобнее генерировать плитку, и такой точности достаточно для бизнес-логики
4. Значение новой плитки выбирается так:
   1. Генерируется случайное целое число от 0 до 999 и переводится в дробь от `0.000` до `0.999` (шаг `0.001`, отсюда ограничение в 3 знака)
   2. Перебираем spawn-правила и накапливаем сумму вероятностей
   3. Как только сгенерированное число становится меньше накопленной суммы, берём кэшбэк из текущего правила
   
   То есть отрезок `[0, 1)` разбивается на участки, длины которых равны вероятностям spawn-правил, и мы смотрим, в какой участок попало случайное число
5. Клетка для новой плитки выбирается случайно среди свободных. Если свободных клеток нет, выбрасывается исключение
6. Поля, которые есть в конфиге, но отсутствуют в `CampaignConfig`, игнорируются
7. Если в конфиге нет поля, которое есть в `CampaignConfig`, выбрасывается исключение

### Поле
Координаты клетки вынесены в `Position`, чтобы было удобнее работать с ними вне класса `Board`: сразу понятно, где строка, а где столбец (с `int[]` непонятно, в каком порядке передавать значения)

### Движок ходов
1. Сдвиг и слияние явно реализованы только для `LEFT`. Остальные ходы обрабатываются так:
   1. Поле преобразуется: `RIGHT` - строки переворачиваются, `UP` - поле транспонируется, `DOWN` - поле транспонируется, потом строки переворачиваются
   2. Вызывается логика для `LEFT`
   3. Поле возвращается в исходную ориентацию
   
   Так логика слияния написана один раз, а не четыре
2. `MoveService.move` не изменяет переданное поле, а возвращает новое. Поэтому им можно прикинуть ход, не меняя состояние игры
3. Логика слияния (`MoveService`) отделена от случайности (`TileSpawner`)
4. У каждой игровой сессии свой `TileSpawner` со своим `Random`, созданным по seed. Поэтому спавнер хранится в сессии, а при одинаковом seed и одинаковых ходах игра всегда проходит одинаково
5. Невалидный ход выбрасывает `InvalidMoveException`, состояние игры при этом не меняется

Сообщения об ошибках вынесены в `messages.properties`
